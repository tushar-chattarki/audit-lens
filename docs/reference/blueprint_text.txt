Executive SummaryThis blueprint upgrades the original 7-member task plan into a hackathon-ready, judge-ready product: an “Audit Copilot” that ingests a bank's financial statements (PDF/Excel), runs deterministic mathematical and consistency checks, uses an LLM strictly for language, explanation and narrative work (never for arithmetic), links every finding to its source evidence, and auto-drafts a WP-514 working paper for human sign-off.The core design principle is separation of certainty from judgment: anything that has one correct numeric answer (totals, cross-casting, prior-year deltas) is computed deterministically in code; anything that requires language or explanatory judgement (grammar, “why did this move” narratives, reviewer commentary) is delegated to an LLM that is only allowed to reason over already-validated numbers — never invent them.The rest of this document gives a concrete technology stack, a layered architecture, full module-level design, a worked real-life example (“GreenPeak Bank Ltd.”) showing the pipeline catching four planted errors end-to-end, a revised 7-person task split with an hour-by-hour build timeline, and guidance on mapping the build to Cognizant's judging criteria (Impact, Innovation, Technical Strength, Scalability).2. Problem Statement & Business ImpactFinancial statement review in banking is high-stakes and still largely manual: reviewers cross-foot totals by hand, eyeball prior-year comparatives for “unusual movements,” manually trace note disclosures back to the primary statements, and write review commentary from scratch. This is slow, inconsistent across reviewers, and easy to get wrong under time pressure — exactly the kind of structured-but-tedious work that benefits from automation with a human still in control of judgement calls and sign-off.2.1 Pain Points → What the Copilot FixesManual Pain PointAutomated FixRe-adding totals/subtotals by hand across BS, P&L, Cash FlowDeterministic math engine cross-foots every statement in secondsComparing current vs prior year figures line by lineAutomated PY delta engine flags material % / absolute movementsManually tracing a note figure back to the statementConsistency engine matches note ↔ statement ↔ cash flow automaticallyWriting review commentary and explaining anomaliesAI layer drafts reviewer-friendly, evidence-grounded narrativePopulating the WP-514 working paper by handValidated findings auto-populate WP-514 draft fieldsNo single view of status across a bank's statement setDashboard shows overall status, severity and drill-down evidence3. Solution OverviewPositioning: this is not “AI that audits a bank.” It is a copilot that removes the mechanical 80% of review work (casting, comparison, tracing, drafting) so a human reviewer spends their time on judgement — materiality, root cause, and sign-off. Three design rules govern every module:Determinism for numbers. Every arithmetic or comparison check (totals, cross-casting, YoY %, note-to-statement matches) is plain code — Python/pandas — never an LLM call. This makes results reproducible and defensible.Grounding for language. The AI layer only ever receives already-validated figures and explicitly labelled findings; it is prompted to explain and phrase, not to calculate or invent numbers.Evidence for trust. Every finding — pass or fail — carries a pointer back to its source: document, page, table/note number, and row/cell reference, so a reviewer can verify in one click.4. Advanced System ArchitectureThe MVP architecture from the original plan is preserved (extraction → canonical data → evidence mapping → parallel engines → findings → WP-514 → dashboard) and extended with an orchestration layer, a findings/risk aggregator, and clearly separated storage. Synthetic data generation stays fully outside the production pipeline, feeding it only as an input file, exactly like a real uploaded statement Detailed Module Design6.1 Document ExtractionGoal: turn an uploaded PDF/XLSX into raw text + tables + a first-pass label of which statement or note each table belongs to (Balance Sheet, P&L, Cash Flow, Equity Statement, Notes 1..n).PDF: pdfplumber for text and simple tables; camelot (lattice mode) for ruled tables typical of bank statements; Tesseract OCR fallback if a page has no extractable text layer (scanned document).Excel: openpyxl/pandas reads each sheet; sheet-name and header heuristics (“Total Assets”, “Net Profit”, “Cash and cash equivalents”) assign a statement label.Every extracted number keeps a pointer: {document_id, page, table_id, row_label, column/period}. This pointer is what the Evidence layer stores.Hackathon scope: optimize first for the team's own synthetic PDFs/XLSX (fixed layout), not arbitrary real-world formats — per the original guardrail.6.2 Canonical Financial Data ModelAll downstream engines read one normalized JSON shape, regardless of source format. Example (abridged):{  "bank_id": "GREENPEAK",  "periods": ["FY2025", "FY2024"],  "statements": {    "balance_sheet": {      "total_assets":       {"FY2025": 1245000, "FY2024": 1102000, "evidence": {...}},      "total_liabilities":  {"FY2025": 1080000, "FY2024": 958000,  "evidence": {...}},      "total_equity":       {"FY2025": 161000,  "FY2024": 144000,  "evidence": {...}},      "cash_and_equivalents": {"FY2025": 125000, "FY2024": 98000,  "evidence": {...}}    },    "profit_and_loss": { "net_income": {"FY2025": 21600, "FY2024": 17800, "evidence": {...}} },    "cash_flow": { "closing_cash": {"FY2025": 120500, "FY2024": 98000, "evidence": {...}} },    "notes": { "note_12_cash": {"FY2025": 120500, "FY2024": 98000, "evidence": {...}} }  }}6.3 Mathematical Engine (Deterministic)Pure functions, one per rule, each returning a pass/fail plus the exact numeric difference and the evidence pointers of every value it used. No LLM involvement.RuleFormula / CheckBalance sheet balancesTotal Assets = Total Liabilities + Total EquityP&L cross-castTotal Income − Total Expenses = Net Profit/(Loss)Cash flow cross-castOpening Cash + Net Cash Flow (Op+Inv+Fin) = Closing CashEquity roll-forwardOpening Equity + Net Income + Other Movements − Dividends = Closing EquitySubtotal/footingEvery disclosed subtotal equals the sum of its component lines6.4 Consistency + Prior-Year Engine (Deterministic)Cross-statement matches: Balance Sheet cash ↔ Cash Flow closing cash ↔ Note on cash & equivalents (must be equal, or flagged).Selected linkages: net income (P&L) feeding the equity roll-forward and the cash-flow statement's operating section starting point; dividends/tax/depreciation appearing consistently across statement and note.Prior-year comparison: for every mapped line item, compute absolute and percentage movement FY(t) vs FY(t-1); flag anything beyond a configurable materiality threshold (e.g. >20% and >₹5 Cr) as “unusual movement” for the AI layer to explain.6.5 AI Layer (LLM-Assisted, Grounded)The AI layer never sees raw documents directly for numeric work — it receives the canonical data plus the deterministic engines' findings, and is instructed to explain, phrase and summarize only. Three sub-tasks:Language review: spelling/grammar pass on extracted narrative text (director's report, note descriptions) — LanguageTool for a fast deterministic pass, LLM to suggest natural rephrasing for anything flagged.Anomaly explanation: given a flagged prior-year movement (e.g. “Other Income up 340%”) plus any related note text, produce a plausible, evidence-grounded explanation candidate and clearly mark it as a suggested explanation for reviewer confirmation, not a fact.Reviewer summary: a short, plain-English roll-up of overall findings by severity, written for a WP-514 reviewer, strictly built from the findings list it was given.Prompting rule: system prompt instructs the model to only use figures present in the supplied JSON, to never introduce a number that isn't in context, and to output structured JSON (finding_id, explanation, confidence, caveats) so it drops straight into the findings table.6.6 WP-514 ModuleOnce findings are validated, the module maps them into the agreed/prototype WP-514 template: reviewed item, expected value, actual value, variance, status (Pass/Exception), evidence reference, and an editable reviewer comment/sign-off field that stays human-controlled by default, matching the original guardrail.6.7 DashboardUpload screen with job status (Extracting → Reviewing → Done).Overall status header: Pass / Exceptions count, by severity (High/Medium/Low).Findings table, filterable by module (Math / Consistency / PY / AI / Disclosure), each row expandable to show the evidence (source page image + highlighted cell).WP-514 tab: the generated working paper, editable, exportable to PDF/Excel.7. What NOT to OverbuildDo not implement every possible accounting rule — ship a strong, tested core (the 5 checks in §6.3/6.4) and keep the rule library extensible.Do not use an LLM for any deterministic calculation — keep that boundary absolute, it is the credibility of the whole product.Do not spend hackathon hours on authentication, microservices, or production infra — one FastAPI process + Docker Compose is enough to demo.Do not build a large dataset — the 9 seeded cases from the original plan (§5 of the source document) are sufficient to prove every module.Do not let the AI layer's explanations look like established fact — always label them as suggested/pending reviewer confirmation.12. Post-Hackathon Scalability RoadmapSwap synchronous checks for an async task queue (Celery/RQ or a lightweight job runner) as document volume grows.Add a rules-config layer (YAML/JSON rule definitions) so new checks don't require code changes.Introduce role-based auth and audit-trail logging once moving beyond demo.Add a vector-indexed note/disclosure store so the AI layer can ground explanations across many notes and prior filings, not just the current document.Support additional input formats (XBRL, scanned/OCR-heavy filings) by extending the extraction layer only — canonical JSON and downstream engines stay untouched.Appendix A — Seeded Test Case MatrixCaseScenarioExpected Result1Clean statementsCore checks pass2Balance Sheet math errorMath engine identifies mismatch and amount3P&L / Cash Flow calculation errorRelevant check fails4Prior-year mismatchPY difference identified5Statement vs note mismatchConsistency issue flagged with evidence6Large unusual movementAnalytics flags it; AI explains it7Spelling/grammar issuesLanguage engine suggests corrections8Missing/inconsistent disclosureDisclosure/WP-514 review flags it where supported9Multiple issues in one bankDashboard consolidates all findings (see §7 walkthrough)Appendix B — One-Line Demo GoalUpload a fictional bank's financial statements → automatically detect planted review issues → show source evidence → explain the issues → populate the applicable WP-514 output — all in a single, judge-facing, end-to-end run.
